# AGENTS.md — правила работы AI-агентов (Codex) с этим репозиторием

## 1) Цель проекта (MVP)
Этот репозиторий — MVP Telegram-бота, который:
- запускается локально;
- обрабатывает запросы пользователей через Telegram;
- использует локальную RAG-базу знаний на **ChromaDB**;
- использует LLM на отдельном сервере с GPU через **Ollama** для обработки/генерации (и максимально — для обработки файлов).

Главная цель: **минимальный, простой, устойчиво запускаемый локально MVP**.

## 2) Запуск и точка входа
Единая каноническая команда запуска:

```bash
python telegram_bot_mvp.py
```

Правило: проект должен запускаться этой командой без дополнительных ручных шагов.

## 3) LLM / GPU / Ollama (обязательно)
- Внешний сервер с GPU и Ollama: переметры подключения в .env.llm
- При обработке файлов и при генерации эмбеддингов/ответов **предпочитай внешний GPU через Ollama**, если это технически возможно.
- Не добавлять альтернативные слои хостинга/оркестрации LLM, не создавать новые сервисы под LLM.

## 4) Жёсткие запреты (MUST NOT)
Запрещено:
- добавлять или требовать **FastAPI**;
- добавлять или требовать **Docker / docker-compose**;
- добавлять инструменты автоматизированного тестирования как обязательную часть MVP (pytest и подобное);
- добавлять сложные системы логирования/наблюдаемости (разрешены только `print()` или стандартный `logging` при крайней необходимости);
- создавать новые сервисы/микросервисы или усложнять архитектуру (многопроцессность, отдельные демоны и т.п.);
- делать рефакторинг “ради красоты”, если это рискует сломать простоту/запуск/поведение MVP.

Общее правило: **никакого over-engineering**.

## 5) Политика зависимостей
- Добавлять зависимости можно, если это приносит прямую пользу MVP.
- Если добавлена/изменена зависимость — ОБЯЗАТЕЛЬНО обновить `requirements.txt`.
- Предпочитать небольшие и распространённые библиотеки. Избегать тяжёлых фреймворков без явной необходимости.

## 6) Конфиги и секреты
Источники истины лежат в корне репозитория:

### `.env`
Хранит:
- токен Telegram;
- пути к локальным каталогам (например, где лежит ChromaDB);
- прочие локальные настройки выполнения.

Правила:
- секреты НЕ хардкодить в коде;
- все параметры читать из `.env` (или переменных окружения).

### `.env.llm`
Хранит:
- настройки, какой класс/стратегия используется для обработки файлов;
- параметры доступа к GPU-серверу (Ollama);
- имя используемой модели.

Правила:
- URL Ollama и имена моделей должны быть конфигурируемыми через `.env.llm`;
- при отсутствии обязательных параметров — завершать операцию корректно, с понятной ошибкой и сообщением пользователю.

## 7) Критерии готовности (Definition of Done)
Изменение считается готовым, если выполнено ВСЁ:
1. `python telegram_bot_mvp.py` запускается без ошибок и без дополнительных ручных действий.
2. Бот доходит до состояния “готов” (например, в консоли видно “Bot started” / “Polling started” или аналогичный понятный признак).
3. Бот умеет:
   - принимать текстовое сообщение;
   - получать запрос от пользователя на обработку файла через спец символ `$`;
   - создавать/обновлять локальную ChromaDB;
   - отвечать пользователю с использованием RAG (retrieval + generation) без падений.
4. Конфигурация соблюдается:
   - токен Telegram берётся из `.env`;
   - настройки LLM (URL Ollama, модель и пр.) берутся из `.env.llm`.
5. Не добавлены запрещённые технологии (см. раздел 4).
6. Все новые зависимости отражены в `requirements.txt`.
7. Ошибки обработаны корректно:
   - пользователь получает дружелюбное сообщение об ошибке;
   - в консоли остаётся минимальная диагностика (что произошло и где искать).

## 8) Стиль кода и комментарии (ОБЯЗАТЕЛЬНО)
- ВЕСЬ новый код должен содержать комментарии **на русском языке**.
- Оформление комментариев — по стандартам Python:
  - docstring для модулей/классов/функций (PEP 257);
  - inline-комментарии только там, где логика неочевидна;
  - комментарии должны объяснять “почему/зачем”, а не повторять очевидное.
- Предпочитать простой и понятный код, без лишних абстракций.

## 9) Дисциплина изменений
- Выполнять изменения небольшими и строго по задаче.
- Не переименовывать и не перемещать файлы без реальной необходимости для MVP.
- Если меняется поведение или появляются новые параметры — обновить документацию (README и/или этот файл).
- Посмотреть code diff и проверить, соответствует ли он стилю кода и руководящим принципам проекта. 
- Просмотрть AGENTS.md и соответствующие правила проекта и обновить их, чтобы они были точными с учетом изменений.
